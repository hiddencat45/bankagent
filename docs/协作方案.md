# 银行 AI 智能体 · 双人 vibecoding 协作方案

> 前提：Demo 优先、两个人、A 用 DSH、B 用 Codex。
> 本方案不动你的现有目录，所有模板自行复制创建。

---

## 0. 先想明白一件事

单人 vibecoding 的瓶颈是**写得慢**，所以"让 AI 多写"就有效。
双人 vibecoding 的瓶颈不是写得慢——是**合并**。两个人、两个 agent，等于四个作者同时往一个代码库里灌代码，每个 agent 都倾向于"重写整个文件让它更好"。

所以整套方法只服务一个目标：

> **让两个人的 agent 在互不重叠的边界里各自狂奔，只在少数几个冻结的接口上碰面。**

推论有三条，后面所有设计都是它们的展开：

1. **接口必须先冻结，代码后写。** 否则 A 的 agent 假设工具返回 `dict`，B 的 agent 返回 `dataclass`，对接时两边返工。
2. **文件必须有唯一所有者。** 没有所有权，两个人的 agent 会同时改 `build_graph()`。
3. **"完成"必须由机器判定。** agent 说"已实现"不算数——它可能实现的是 PPT 里承诺但代码里没有的能力，你的项目里这种风险特别高（34 页 PPT 描述 6 场景，代码只有 1 个）。

### 你现在的三个硬阻塞

| 阻塞 | 影响 | 对应步骤 |
|---|---|---|
| `bankagent/` 不在任何 git 仓库里 | 无法协作，改同一文件只能互相覆盖 | 步骤 1 |
| `langgraph` 在当前 Python 环境里没装（`pip show` 查不到，但 `__pycache__` 有 10/8 的 `.pyc`） | 11 条测试现在跑不了，队友 clone 下来也跑不起来 | 步骤 1 |
| 代码是单文件 `bank_agent_graph.py`（583 行，State + 全部节点 + 图组装） | 两人任何改动都在同一文件里打架 | 步骤 2 |

   你的 `gh` 已装但**未登录**（`gh auth status` 报 not logged into any GitHub hosts），先 `gh auth login`。
   git 全局身份已配好：`hiddencat45 / shiwenfeng123@hotmail.com`。

### 步骤 3 · 冻结契约（约半天，两人必须一起做）

这是全套方案里**唯一不能省**的一步。契约没冻结就分工，等于两人朝不同方向跑。

做法：把 34 页 PPT 里已经写好的设计，翻译成 3 个机器可读的契约文件。

**A 起草 `state.md` 和 `api.md`，B 起草 `tools.md`，然后互相挑错。** 挑错的标准只有一条：*照这份契约写代码，能不能不问我任何问题？*

`tools.md` 是重头戏，因为 6 场景的工具是你 PPT 第 17–24 页的核心内容。我已按你 PPT 里的设计整理好初稿放在 §4.4，直接拿去用。

冻结后的规则（写进 `AGENTS.md`）：

> 改 `docs/contracts/` 或 `src/bankagent/contracts/` 的任何文件，必须两人同时在场确认，并且单独开一个 `contract:` 分支的 PR。
> **任何 agent 都不许自行修改契约来"让代码跑通"。**

这条是整套方案的安全阀。没有它，agent 遇到不匹配时会去改契约而不是改代码，契约就废了。

验收：两人各自能照着契约独立写出一段能跑的代码，不需要问对方任何问题。

### 步骤 4 · 分工与并行（持续）

**分法：骨架 vs 血肉。** 不是按层切也不是按场景切——是按"谁碰图、谁不碰图"切。

| | A（你，DSH） | B（队友，Codex） |
|---|---|---|
| **领地** | `src/bankagent/graph/`、`src/bankagent/contracts/` | `src/bankagent/tools/`、`data/`、`api/`、`frontend/` |
| **做什么** | State 契约、图组装、4 处条件边、`security_policy`、hash/challenge、interrupt 与执行、幂等与审计挂点 | 6 场景工具函数、模拟数据流水线 + 一致性校验、FastAPI + SSE、最简演示前端 |
| **为什么这么分** | LangGraph 那套逻辑你已经吃透（PPT 第 1–16 页就是它），也是评委最看重的部分 | 工具是纯函数，可独立测试，B 不需要懂 LangGraph 就能干活 |
| **验收** | 图结构与安全路径测试绿 | 工具契约测试绿 + API 能起 |

**为什么这个分法对 2 人最优**：两人只在**一个**接口上碰面——`contracts/tool_spec.py`。B 按签名实现工具函数就能独立跑测试；A 按契约调用就能组装图，甚至可以先用 **Fake 工具**（返回写死的 dict）把图跑通，不必等 B。

这就是契约先行带来的**真正并行**：

```
第 1 天    A: 把图拆好 + 用 Fake 工具让 6 场景的图都跑通
           B: 按契约实现 6 场景工具 + 各自的单测（不碰图）
                            ↓ 各自独立，互不阻塞
第 3 天    A: 图跑通 → 把 Fake 换成真工具（改一行 import）
           B: 工具跑通 → 开始写 API 层
                            ↓ 在 contracts 处对接
第 5 天    端到端 Demo 第一次跑通
```

**关键约定**：A 的 Fake 工具放在 `tests/fakes.py`，**不要**放在 `src/` 里，避免和 B 的真实现撞名。

顺序上建议：**先做转账 + 账单两个场景打通端到端**（一个已有一半、一个是纯查询最简单），跑通后再批量做剩下 4 个。不要在 6 个场景之间平均用力——Demo 优先的意思是先有一条能演的线。

---

### 步骤 5 · 门禁与交叉 review（持续）

**5.1 一键门禁 `scripts/check.ps1`**

任何人（和任何 agent）在说"做完了"之前必须跑它，内容见 §4.5。四件事：

1. `pytest` 全绿
2. **契约一致性测试**（见下）
3. 依赖没被偷加（对比 `requirements.txt`）
4. 敏感词扫描（密码、OTP、真实卡号格式）

**5.2 契约一致性测试**（`tests/test_contracts.py`）

这是防止 AI 漂移的核心装置，也是你项目里最值得加的一条测试：

> 解析 `docs/contracts/tools.md` 里列出的工具名与签名，断言它们在 `tools/registry.py` 里真实存在、参数名一致、风险等级一致。

这样 agent 一旦偷偷改了工具名或参数，测试立刻红。**文档和代码再也不会各说各话**——这正是你 PPT 里"未实现却写成已实现"风险的机器化防线。

**5.3 交叉 agent review（2 人 vibecoding 的效率关键）**

两人互审会变成瓶颈。改成**让对方的 agent 审**：

- A 写完 PR → **B 用自己的 Codex 审** A 的代码
- B 写完 PR → **A 用自己的 DSH 审** B 的代码

固定的 review prompt（照抄，见 §4.7）：

```
审查这个 PR 的 diff。逐条回答：
1. 有没有改动 docs/contracts/ 或 src/bankagent/contracts/？如果有，列出来。
2. 有没有越界修改不属于自己领地的文件？
3. 有没有违背 AGENTS.md「安全边界」那几条？（模型可写字段、interrupt 前副作用、float 金额、认证来源）
4. 新增行为有没有对应测试？测试是否真的会失败（而不是恒真）？
5. 有没有声称实现了 PPT 里有、代码里没有的能力？对照 docs/contracts/ 判断。
6. 有没有新增第三方依赖？
只报问题，不要复述代码，不要夸奖。
```

这样每次 review 只花 1 分钟，而且 agent 抓安全越界的准确率比人高。**人只负责裁决 agent 报出来的问题。**

## 2. 六条铁律

贴在 `AGENTS.md` 里，也贴在你们的工作群里：

1. **契约先行。** 改契约必须两人同时在场，且单独开 `contract:` 分支。agent 不许为跑通代码而改契约。
2. **文件有主人。** `graph/` 是 A 的，`tools/`+`data/`+`api/`+`frontend/` 是 B 的。跨区改动先在群里说一句。
3. **一个任务 = 一个分支 = 一个 PR，diff 尽量 < 400 行。** 超过 400 行的 PR，agent 和人都审不出问题，等于没审。
4. **交叉 agent review。** 你的代码让他的 agent 审，他的代码让你的 agent 审。
5. **测试是唯一验收。** agent 说"已完成"不算完成，`check.ps1` 绿了才算。
6. **每轮结束同步 `TASKS.md` 和 `DECISIONS.md`。** 群里口头定的结论不落盘，下一轮 agent 就会按自己的理解重做一遍。

## 5. 两个容易被忽略但很值钱的点

**5.1 让 agent 读 PPT 的生成脚本，而不是读 PPT**

`build_bank_agent_deck.js`（245 KB）里逐页写着 6 场景的工具、风险等级、安全边界，是纯文本、可 grep、可 diff。让 agent 从它里面取设计意图，比截图或转述准确得多。契约初稿我就是这么整理的。

**5.2 把"未实现"显式标注在代码里**

你的 PPT 里已经标了 `[源码已实现（转账）]` / `[设计目标，待实现]`，代码里也要有同样的标记，例如：

```python
# STATUS: 设计目标，未实现。见 docs/contracts/tools.md#账单分析
def detect_anomalies(...): ...
```

这样 agent 读代码时不会把"设计目标"误当成"已有能力"去调用，交叉 review 的第 5 条也有据可查。**这是防止 AI 幻觉出不存在功能的最低成本手段。**
