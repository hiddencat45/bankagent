# 双人 Agent 协作方案

> 当前执行版。面向两位开发者及各自的 AI 助手；取代本文件旧版排期和模板。
> 目标：先交付可运行、可解释的比赛 Demo，再扩展场景。不要为了协作框架而额外搭框架。

## 1. 开工前只做这些

1. 读根目录 `AGENTS.md`；涉及业务时再读 `docs/场景扩展与分工.md`。
2. 检查当前分支、未提交改动和相关代码。保留用户已有修改，不混入本任务提交。
3. 确认自己是 A 还是 B、这次做什么、允许改哪些文件。身份由用户指定，不能仅按 AI 产品名推断。
4. 一个任务一个分支一个 PR；已有对应任务分支就继续使用。不要直接向 main 提交或推送。

当前代码仍在 `preparaion/`，只有余额查询和转账教学流程；其余场景、API、前端是待实现内容。PPT 生成脚本用于读取设计意图，不能作为已实现能力的证据。

## 1.1 比赛要做出来的效果（团队目标，不是官方评分表）

依据 `preparaion/build_bank_agent_deck.js` 的交互、场景、数据与总结部分，以及 `build_frontend_mockup.js` 和预览 PNG，产品应让用户通过对话办理模拟银行业务，看到可核查的分析、需本人确认的操作卡片和实际执行进度。

| 展示目标 | 最小可验证效果 |
|---|---|
| 能理解请求 | 不只支持一句固定口令；对同一意图的不同表达能提取候选参数，缺字段能澄清 |
| 分析有依据 | 账单总额由后端算，异常结论可查看交易证据；界面与后端金额一致 |
| 办理有边界 | 转账先展示确认卡，取消后不扣款；越权、余额不足、认证失败有明确结果 |
| 过程可见 | 页面显示查询、待确认、执行、完成或失败；这些来自后端实际事件，不是定时播放的假进度 |
| 结果可复现 | 固定种子和参考日期；转账后余额与账本一致；仅重置演示数据即可再次演示 |

工作台可以复用预览的“账户概览＋对话业务卡片＋执行轨迹”布局和视觉风格，不要求逐像素复制。未实现的入口隐藏或标为未开放，服务状态来自实际检查。轨迹只显示业务步骤、风险摘要和证据，不展示模型内部思维或敏感信息。

预览中的“分析消费，顺便转账”是复合请求的设计目标：第一阶段可以明确引导拆分；支持后必须逐项显示结果、单独确认写操作，不能只识别“转账”就丢掉前半句。固定联动不等于通用任务编排。

六场景仍是团队总体目标。转账＋账单先闭环，随后卡片、订阅、理财、固定联动逐项验收；若时间不足，agent 提供“已有能力、剩余工作、建议取舍”，由双方决定删减，不能自行把未实现项视为不需要。

用户已确认参加[比赛网站](https://fintechathon.g-ican.com/#/)的人工智能赛道，并明确**项目本身优先，不必围绕赛事规则过度设计**。官方细则尚未核实，赛道信息来自用户确认；截止日期、演示时长等仍未知。agent 按项目目标持续开发，不因缺少评分表停工、不反复索取规则，也不增加迎合假定评分项的功能。提交前再核对提交形式、期限及模型使用等必要约束；只有明确冲突才提出最小调整。

## 1.2 模型与现场稳定性

- A 负责模型适配和多轮澄清，B 提供脱敏的业务事实与证据样例。阶段 0 先约定候选输出，阶段 2 接入可替换的真实模型；供应商、模型、凭据和预算未定时先完成适配边界与离线测试，不假装已接通。
- 真实模型至少用于意图/槽位理解；账单说明可基于后端结果组织。计划校验、金额计算、风险、授权和写入仍由程序负责。接口允许模型返回候选，不能扩大到可信字段。
- 保留明确标注的离线规则模式，模型超时、不可用或输出非法时显示失败/澄清或提示切换模式，不能静默假装模型成功，更不能默认批准写操作。
- 单测用固定模型替身，实际接入另做少量端到端验证。密钥通过环境变量等受控配置提供；只记录所需变量名，不进入源码、前端、示例或日志。
- 不默认增加向量库、通用 DAG、真实银行支付或完整生产认证。RAG 仅在需要政策/产品来源问答且有资料时独立排期；不能用知识库替代实时业务查询。

## 1.3 交付时双方必须能复演

阶段 2 首次跑通时，由 A 在根目录 README 记录实际安装、启动、模型配置方式及演示步骤，B 补充模拟数据初始化/重置方式与页面启动步骤；随实现更新，不另建多份重复交付清单。

- 固定演示至少包含：账单分析及证据、转账确认成功、取消或拒绝、失败提示；若已实现多轮补全，再演示只补缺失字段。真实模型用几种同义表达验证，不只测写死台词。
- 页面、图结果、后端状态三者核对一致；重复点击不能产生重复写入。模拟后端是可变的业务状态，不是每次都返回相同成功文案。
- 记录演示模式（真实模型/离线规则）、模拟认证、内存存储重启行为、未实现能力，以及实际运行命令与检查结果。重置仅影响演示数据。
- 最终 PPT 以实际演示能力更新，保留设计目标标记；界面样稿不算已实现页面。PPT/图生成脚本依赖本机外部 `.dsh` 路径，只有本次需要重生成时才处理可移植性，不宣称队友 clone 后已能生成。

## 2. 采用一套结构，不同时做两次重构

本轮采用 `preparaion/` 下的轻量场景模块方案，具体目录见《场景扩展与分工》。暂不迁往 `src/`，不改 `preparaion` 拼写。

- A 负责公共图、调度、安全、转账和卡片场景，以及 API 接入与模型适配。
- B 负责后端操作、模拟数据、账单、订阅和理财场景，以及最小演示页面。
- 双方共同确认接口；各自为自己的行为写测试。
- B 的后端是 A 的依赖：先交付转账所需操作，随后按当前里程碑交付，不能只交函数壳就称场景完成。
- 任一方工作积压时，都可转交一个明确的完整任务（包括实现和测试），在 PR/任务交接中写明临时所有权；不要只转交薄薄的场景文件。

目录所有权是避免同时修改同一文件的约定，不是永久限制。任务已经明确授权跨目录修改时，无需重复询问；发现未约定的跨人改动，先说明涉及文件和原因，与负责人协调。不要擅自重写对方模块。

## 3. 按可演示结果推进，不承诺五天做完六个场景

| 阶段 | A | B | 可以进入下一阶段的条件 |
|---|---|---|---|
| 0：最小接口 | 起草公共状态、场景接口、API 请求与事件格式 | 起草当前要用的后端签名、结果和最小数据样例 | 双方在 PR 确认；明确每个函数由谁实现 |
| 1：现有流程模块化 | 提取转账逻辑，再单独实现公共调度和安全校验 | 提取模拟后端，提供转账/余额实现 | 原测试通过；新调度有测试；未改变现有行为的部分可对照验证 |
| 2：第一条 Demo | 接 API、确认恢复、模型适配与多轮澄清 | 完成账单、后端数据与最小演示页面 | 页面能查询账单和演示转账，成功、拒绝、失败均可演示；模型/离线模式明确 |
| 3：扩场景 | 卡片场景、公共接入支持 | 卡片后端、订阅、理财按优先级推进 | 每个场景通过后端与图的集成测试；范围删减须双方确认 |
| 4：交付收口 | 固定跨场景演示、PPT 与答辩 | 联调、数据与缺陷修复 | 用固定演示脚本从头跑通，清楚标明未实现项 |

阶段内可以并行，但依赖项没有就使用测试替身，不能把替身当成已交付。数据开发先约定账户、交易等最小字段和固定样例，再做生成器。页面从阶段 2 开始做，不留到交付最后一天。

机械迁移与新功能分开提交，最好分开 PR；自动发现、通用调度属于行为改造，要另有测试。原有 11 条测试通过是回归基线，不是“纯搬运”或新能力正确性的证明。

## 4. 接口怎么确认，怎么避免等人

只冻结当前阶段需要的接口，不一次设计完六场景。接口至少写明：函数名、参数类型与来源、返回结构、失败语义、是否写操作、负责人与测试样例。

- 由 A/B 任一方起草，双方通过 PR 留下确认即可，不要求同时在线。
- 后端签名先写入 `preparaion/bank_backend.py`；未实现函数抛 `NotImplementedError`。
- 测试替身放 `preparaion/tests/`，仅用于测试。运行时遇到未实现操作应明确报告不支持/不可用，不能吞掉异常返回成功。
- 接口变更包括后端公开签名、公共 State、操作声明和结果结构，单独走 `contract/<简述>` PR；双方确认后接入。普通函数内部实现不算契约变更。
- 发现接口缺口时，提出最小修改与受影响调用方，继续做不依赖它的工作，不要整项停工或私自改契约适配自己。

不强制维护多份重复契约文档。已确认的代码类型、签名和测试样例是实现依据，本文负责流程说明。API 开工前同样先确认请求、事件、恢复和错误格式，不从公开请求直接构造内部 State。

## 5. 日常交接：一张任务卡就够

任务可写在 PR 描述或发给 agent 的消息中，不强制同时维护 TASKS、DECISIONS 等看板。

```text
角色：A / B
目标：本次可观察到的结果
分支：feat/... 或 fix/...、refactor/...、docs/...、contract/...
可改文件：具体路径；如有跨人授权，在这里写明
接口依据：已确认 PR / 代码位置
依赖：等谁的哪个函数；没有依赖就写无
验收：用户输入、期望结果、必须覆盖的失败情况
交接：实现了什么、怎么运行、检查结果、未实现项及下一步
```

agent 可以自行决定局部实现、变量名、测试组织，不需要逐项请示。仅当修改公共接口、安全规则、任务范围或他人正在改的文件时协调；已有授权不重复索取。

用户只说“开工/继续”时，先查当前里程碑、已合并接口和未完成任务，提出并执行自己领地内的最小下一步，不重复从头规划。首次接口由 A 起草、B 补充审查，使用同一份 PR，不各建一套。向用户交接“已完成、怎么验证、下一步、需对方处理的事项”；需带给另一位 agent 的内容给出可直接复制的任务卡，不要求用户解释类型系统或框架细节。

## 6. 合并与检查

- 提交只包含本任务文件；提交格式为 `<类型>(<范围>): <中文简述>`。
- diff 尽量小于 400 行。机械移动或删除旧文档导致超出时，在 PR 中解释；不要为了凑行数拆成无法验证的碎片。
- 用 `.venv` 执行 `scripts/check.ps1`；新增测试必须被实际收集。API/页面涉及的启动和端到端验证另行执行，Python 测试全绿不能代替页面可用。
- 当前门禁的敏感字段扫描仅提示，`pip check` 只检查依赖一致性；不要声称它们已全面检查泄露或锁定文件漂移。
- 对方 agent 可辅助审查，但合并仍需对方开发者确认。测试通过和 AI 审查都不能替代这一步。
- 合并前一刻重新核对 PR 头 SHA 是否等于已审查过的那个。PR 在审查后可能又推了新提交，此时必须重新审查增量，不能凭之前的结论合并。
- 依赖确需增加时说明用途、更新锁定文件，只装进 `.venv`；不要顺带升级无关依赖。

给审查 agent 的简短提示：

> 审查 diff 与受影响调用链，优先报告会导致错误执行、越权、丢状态、重复写入和联调失败的问题。检查接口是否双方确认、测试是否覆盖新增失败路径、是否混入用户原有改动。给出文件位置、触发条件和最小修正建议。区分阻断问题与可选建议；不要把目录偏好当成缺陷。
