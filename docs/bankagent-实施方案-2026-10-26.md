## 1. 我们最终要交付什么

一个具有独立应用窗口的本地桌面应用，包含可操作的银行模拟后端和真正由大模型驱动的业务助手。用户既能在普通页面办理业务，也能自然地向助手表达目标；两种入口使用同一套业务服务、同一份数据，操作后同步展示实际结果。

用户直接打开桌面应用使用，无需手动启动后端或在浏览器输入网址。应用负责启动所需的本地服务，业务数据保存在本地。内部可以使用网页技术构建界面并封装为桌面应用，具体技术方案尚未确定；最终交付形态是本地桌面应用，不是浏览器网页应用。大模型可以通过在线服务接入，本地运行不等于完全离线。

核心体验：理解自然表达和上下文 → 查询必要信息 → 澄清歧义或补齐参数 → 提出明确操作 → 用户确认或认证 → 实际执行 → 依据结果继续查询、解释或结束。多步骤请求按依赖执行，不能只处理一句话里的一个关键词。

这不是要训练自己的语言模型，也不是重新实现完整银行核心系统。开发价值在于把现有大模型接入有业务规则、有状态、有实际后果的系统，让它可靠地完成用户任务。模拟后端本身也必须能独立运行，不能仅给对话提供固定成功台词。

## 3. 银行模拟系统应具备的内容

### 3.1 客户、账户与卡不是同一个东西

客户代表使用者，账户保存资金与交易关系，卡是关联账户的支付凭据。卡的冻结状态与账户状态分别建模，不用一个布尔值控制所有业务。

支持至少两个模拟客户，方便验证收款方实际到账；客户可以持有多个账户，便于验证自己账户间转账。演示客户、卡号及身份资料均为明确的虚构数据，展示使用脱敏标识，不要求提交真实身份信息。

开户时创建账户并建立客户归属。申请卡后进入待激活状态，激活后才允许卡支付。卡号/账户标识由后端产生，不由模型自行编造。初始余额通过可追溯的演示入账建立，普通操作页面不提供任意改余额入口。

客户注册、开户与卡申请流程模拟银行业务关系，不声称完成真实实名核验、清算或实体卡制作寄送。

### 3.2 卡包与模拟消费

本次只做本行实体借记卡。“工资卡”“日常消费卡”是昵称或用途，不为名字单独设计不同卡种引擎。

必要状态：待激活、正常、冻结。基本规则如下：

- 未激活或冻结的卡不能完成新的模拟卡支付。
- 解冻后恢复支付资格，但仍需检查余额、限额等条件。
- 冻结卡片不删除历史交易，不扣减余额，也不自动等于冻结整个账户。
- 账户转账是否允许取决于账户及转账规则，不应因为某张卡被冻结就一概禁止。
- 消费限额属于支付控制，和信用额度无关；检查按明确的交易范围和业务日期计算。

提供一个小型模拟消费入口：选择演示商户、卡和金额，后端执行支付。它用于证明卡状态和限额确实生效，不需要建设商城、订单配送或支付网络。消费成功后减少账户余额并生成可查询流水，拒绝时不给出成功流水。

### 3.3 即时转账与批量操作

转账业务统一为付款账户 → 收款账户 → 金额 → 确认/认证 → 记账。转给自己或别人主要是对象选择方式不同，不复制两套资金逻辑。

- 通过账户/卡号或已保存联系人解析收款方；姓名、备注等必须能映射到实际对象，同名则询问。
- 若支持手机号查找，只使用演示联系人映射，不声称可通过任意手机号找到真实银行账户。
- 收付款对象、金额和实际影响必须在确认前展示。
- “改成两百”“换另一个人”更新草稿并重新确认，不能复用旧授权执行新内容。
- “取消”“不转了”或取消按钮结束未执行的操作；已完成转账不能假装撤回。
- 同银行模拟系统内，付款方扣款、收款方入账、关联流水和请求结果在同一事务中保存。
- 金额使用整数分或 Decimal；转账不算商户消费，账单统计要区分资金流动与消费支出。

明确的批量指令按用户讨论结果采用一次确认，列全收款方、金额与总额。确认绑定具体列表；若后续增加或修改写操作，需要再次确认。需要更高等级认证时不能用“一次确认”跳过认证。

2026-10-27 用户明确选择：批量采用整批全有或全无。复用单笔转账的归属、授权、额度、双边记账和幂等逻辑，在同一事务中提交整个已确认列表及回执。任一项校验或事务失败，整批不扣款、不入账；失败项与其他未执行项分开显示，不将暂存步骤标为成功，不用反向转账模拟回滚。成功及业务拒绝的整批回执可在重启后从桌面查询；网络响应丢失时重试原确认不得重复扣款。此前“每笔独立原子交易”仅为建议，已被此决定取代。

### 3.4 账单与基础分析

包括交易列表、消费总额、分类汇总，以及时间、类别、商户、金额等条件筛选。区分收入、消费和转账，不将所有扣款都算作消费。

自然表达例子：“最近钱花在哪里了”“上个月吃饭花了多少”“只看超过一百的”“那交通呢”“列出这几笔”。系统保留必要的查询条件，识别用户是在继承还是替换条件，结果含明确时间范围和可查看的明细。

“最近”采用清楚展示的默认范围；歧义会影响结果时询问，不能每个普通表达都要求补齐完整表单。金额、分类和排序由后端计算，模型负责组织解释，不从文本猜测账目。

不做同比/环比、异常检测、未经用户要求的预算控制；理财推荐走独立的画像与产品筛选流程，不从账单查询擅自延伸为投资建议。可以展示不同月份的账单以支持查询，但这不等于实现跨期比较功能。

### 3.5 数据保存与重置

推荐 SQLite，原因是本地部署简单、提供事务和查询能力，适合当前单机应用；不是因为它等于银行生产数据库。

持久保存客户、账户、卡片、交易及关联记录、消费控制、已执行请求结果。不能只保存余额却丢失防重复执行记录。数据模型必须能够解释一笔转账的双方变化，能够由记录核对余额变动。

初始样例涵盖当前月和上月、不同商户/类别、多个客户账户。样例通过初始化流程生成；之后的记录由实际业务操作产生。基准日期及“本月”的计算一致，避免演示日期与服务器日期脱节。

- 应用内界面刷新、退出后重新打开及正常重启不清空业务数据。
- 明确的重置入口恢复基线并清理失效的会话/授权，不在普通启动时自动重置。
- 重启后不自动执行遗留待确认任务。建议提示重新发起或重新确认。
- 已完成操作在重启后仍可查询，原请求重试不能再扣款。
- 聊天记录是否跨重启保存单独确定；不为长期记忆预先引入向量数据库。

### 3.6 用户数据与字段建议

业务数据按关系分开保存，不把全部内容塞进一个用户对象。以下为逻辑字段建议，具体表结构、类型和命名在实现时确定，不代表现有代码已经具备。

| 数据类别 | 建议字段 |
|---|---|
| 客户 | 客户 ID、虚构姓名、创建时间 |
| 账户 | 账户 ID、账户标识、所属客户、名称、余额、状态、开户时间 |
| 银行卡 | 卡片 ID、卡号、所属客户、关联账户、昵称、状态、申请及激活时间 |
| 消费控制 | 卡片引用、限额金额、限额类型、统计周期、更新时间 |
| 交易 | 交易 ID、账户引用、类型、方向、金额、时间、交易后余额、备注 |
| 消费详情 | 交易及卡片引用、商户、类别 |
| 转账详情 | 转账 ID、付款及收款账户、金额、执行时间、双方流水关联 |
| 联系人 | 联系人 ID、所属客户、名称或备注、收款账户引用 |
| 操作结果 | 请求 ID、发起客户、操作类型与参数、状态、关联交易、失败原因、创建及完成时间 |

会话身份、待确认操作、授权记录与聊天上下文另行管理，不混同账务记录。真实身份信息和信用业务字段不是当前必需项。模型只能获得办理当前任务所需的受控、脱敏数据，不能直接操作数据库。

### 3.7 理财推荐与投资画像

本次明确包含理财产品推荐，不包含购买或赎回。推荐依据由后端产品目录、用户资料及明确的筛选规则提供；模型负责自然补问、组织解释，不编造产品、收益或可信风险等级。

投资画像建议独立保存，包含：理财目标、投资预算、预计持有期限或用款日期、流动性需求、需保留的备用资金、收入稳定性与负债负担、损失承受能力、风险意愿、投资知识与经验、已有投资情况、产品偏好及限制。风险评估记录保存问卷答案、规则版本、评估结果和评估时间。

关键资料记录来源、更新时间和是否经用户确认。区分用户申报、系统统计及规则评估结果：账户余额不等于可投资金额，账单数据不代表全部资产负债，愿意冒险不等于承受得起损失。缺失字段标为未知，不默认为无负债或低风险。信息不足、矛盾或已过期时补问；保存或修改画像属于写操作，沿用确认机制。

产品目录至少包含产品标识、名称、风险等级、期限、起投金额、赎回条件、费用及收益表述依据；演示产品明确标注虚构，不承诺收益。先由后端规则按预算、期限、流动性及风险评估筛选，再由模型解释匹配原因和限制。没有匹配产品时如实说明，不强行推荐。规则与问卷属于模拟评估，不声称完成真实银行适当性审查。

### 3.8 模拟数据生成与规模建议

采用“预设典型用户 + 规则生成交易 + 模拟问卷”的方式，不独立随机拼凑所有字段，也不使用这些数据训练模型。先定义人物情境、收入与支出习惯、资金目标，再生成一致的账户流水与问卷资料；余额由演示入账和实际交易推导。

| 对象 | 第一版建议规模 |
|---|---|
| 模拟客户 | 12 位 |
| 账户 | 每人 1～3 个，总计约 20～25 个 |
| 借记卡 | 每人 1～2 张，覆盖不同状态 |
| 历史流水 | 每人 100～200 条，覆盖近 3 个月，总计约 1,200～2,400 条 |
| 投资画像 | 每人 1 份，包含完整、缺失或待更新状态 |
| 虚构理财产品 | 15～20 款 |
| 推荐验收案例 | 30～50 个 |

以上是可调整的建议，不是最低交付数量。覆盖新手、保守用户、收入不稳定、近期用款、长期投资、持仓集中、意愿与能力不一致，以及资料缺失、矛盾、过期和无匹配产品等情况，比追求大量随机用户重要。

使用固定随机种子和统一演示基准日期，初始化可复现；之后的消费、转账和画像修改由真实业务操作生成。跨账户转账通过同一业务逻辑生成双方记录。用户申报的外部资产、负债不冒充系统查询所得。

代码仓库保存生成规则及必要的虚构演示样例，运行数据库、聊天记录、密钥和运行日志不提交 Git。数据库文件存放位置与聊天记录持久化策略仍待确定。

## 4. Agent 如何实现，而不是只增加聊天兜底

### 4.1 主回路

用户消息及当前上下文 → 模型决定回答、澄清或调用工具 → 程序校验工具与候选参数 → 查询/准备操作 → 将受控业务结果提供给模型 → 继续下一步或输出结果。

写操作进入确认或认证关口，批准后才由业务后端执行。模型可以提出多步骤计划，但不决定自己是否获授权，不制造可信对象 ID、账户余额、风险等级或成功结果。

简单查询不强制生成冗长计划。复杂请求记录必要的步骤、依赖和实际状态；先用小而明确的数据结构，不搭工作流平台或多智能体团队。模型根据工具结果选择下一步，不是把多条固定函数写死为“自主规划”。

### 4.2 工具设计

工具围绕清楚的业务动作组织：查账户、查流水/汇总、查卡、解析收款方、准备转账、准备卡片变更等。真正的执行函数通过受控授权路径调用，普通页面与 AI 复用同一业务服务。

工具返回稳定的业务结果、可解释的错误及必要的引用。向模型暴露受控的对象引用和脱敏业务事实，后端再次解析并校验归属；不把任意模型字段直接合并进内部状态。

不为每个文件设计一个 Agent，不默认增加 RAG、向量库、自动代码执行器、微服务或消息队列。银行实时信息通过业务查询获得，不用知识库替代余额查询。

### 4.3 上下文、纠正与切换

区分消息历史、当前查询条件、展示对象列表、待处理任务与授权状态。不能只把所有聊天拼成字符串，也不能用一个全局“待确认”锁住全部交互。

支持缺项补全、选择“第一个/那张卡”、修改金额或对象、拒绝、取消、切换话题。最新请求优先；用户问余额时先处理查询，旧转账不自动执行。

建议区分：明确取消则删除待办；明确修改则更新草稿并使旧确认失效；无关查询可暂存未执行草稿并清楚标记。是否保留旧草稿的界面细节仍可在实现时细化，不能把“先查一下余额”理解为批准转账。

能力咨询和简单闲聊可以自然回应；涉及个人业务事实先查工具；超范围事项明确解释。不能通过自由聊天通道声称完成银行操作。

真实模型是正式体验，规则模式只用于明确标注的离线演示或开发。供应商故障必须显示状态，不能悄悄切成关键词模式并宣称模型成功。

### 4.4 模型配置与职责

本方案尚未指定模型供应商或型号，不代表现有仓库没有模型接入。正式体验要求真实模型支持中文自然表达、多轮上下文和工具调用回路。建议把 API 地址、模型名称及服务端密钥配置化，按工具调用稳定性、中文理解、响应时间和费用验证后确定选型。

模型负责理解、补问、选择工具和解释；金额计算、产品硬性条件筛选、权限、授权与实际执行由后端负责。模型调用参数和工具返回结果采用结构化数据，不能据此把用户界面做成 JSON 输出窗口。

## 5. 确认、认证和失败：保留必要机制，避免堆防御代码

本节补足尚未详细讨论的实现建议，不把建议冒充旧共识。

- 查询按权限直接执行；写操作确认；高风险按明确策略追加认证。强认证演示与生产身份验证区分标注。
- 认证通过专门界面和服务端处理，不要求在聊天里发送密码或验证码。
- 确认内容和执行参数使用同一份服务端操作记录。防止过期、参数变更及重复执行，但不把内部哈希铺满用户界面。
- 同一笔转账使用数据库事务保存全部变化。响应丢失显示“结果待核实”，先查询原请求结果，不能马上创建第二笔转账。
- 余额不足、卡冻结、对象不明确等可预期问题直接说明原因和下一步；系统异常保留脱敏诊断，不伪造成功兜底。
- 连续认证失败/明显异常请求使用有限、可解释的限制，不扩建完整风控平台。
- 多步骤中断展示已完成、待处理和失败部分；未提交草稿可撤销，已落账资金操作不假装能通过回滚聊天撤销。
- “人工接管”先体现为用户接过表单、修改/取消计划，不能把不存在的客服通道标成已接入。

校验集中在外部请求、模型输出、授权和资金业务边界。内部数据契约清晰后，不层层重复类型猜测，不为任意假想返回值增加静默兼容，不为删哈希而删掉防重复扣款机制。

## 6. 界面与回答呈现

目标是具有独立窗口的本地桌面银行应用，包含账户概览、账单、卡包、转账及 AI 入口。布局和视觉尚未定稿，先以一条可操作流程制作原型，避免先花大量时间整体换前端框架。

2026-10-27 执行状态：在统一任务回路及整批原子转账待审分支上，新增独立入口的两页 PySide6 预览，只接账户概览和转账，原入口保持。实际窗口已复演改金额、确认付款及助手查余额；[设计和证据](桌面应用.md#账户与转账两页预览2026-10-27待认可)。下一步先取得用户对方向的反馈，再扩展其余业务页；不复用已否定的 #58、不切换技术栈，不将预览标为全部视觉交付。

呈现按任务选择：简短问题用文字；分类汇总用简洁图表配金额；多笔交易用明细；写操作用确认卡和结果回执。用户可点开依据，但默认不满屏 JSON、工具名、ID 和技术轨迹。

执行状态、金额、对象和时间由可信业务结果确定性展示；模型负责解释和对话衔接，不让润色层随意把失败改成成功。最终回执和当前状态区别展示，旧回执不能冒充卡片最新状态。

对话冻结卡片，卡包随之更新；页面完成转账，助手随后能查到；模拟支付成功，余额和账单同步变化。所有入口共享业务服务，不各自修改前端缓存伪造成功。

### 6.1 自然回答与对话示例的含义

面向用户使用受事实和业务边界约束的自然语言，不要求每句话套固定模板，也不让模型自由生成关键金额、授权或成功状态。查询可用简短解释，分析配图表和明细，写操作使用确定性确认卡和回执。

- “你有哪些功能”：说明实际可用功能；目标范围包括账户与账单、转账、卡片、开户申请及理财推荐。尚未实现的能力不能宣称已可用。
- “我想转账”：自然询问缺少的收款对象和金额，不强迫一次填写完整表单。
- “给张三转40”：保留张三和 40 元，先用现有联系人或受控解析工具查找；唯一匹配时不重复索要已有账号，同名或找不到时再询问。付款账户需要选择时继续补问，完成确认前不扣款。模拟问答里直接索要账号只是示例，不是每次都必须索要的规则。
- “有没有适合我的理财产品”：查询已有画像，只补问必要的预算、期限、风险等缺项。此前的未批准转账不因切换到推荐而执行；草稿保留与否以真实任务状态为准，不用固定话术假称已保存。

### 7.1 现有代码如何处理

此前核对说明：现有后端确有余额和流水更新，不是纯静态页面；但单边转账、内存保存、业务后果浅等不足需要改造。远端已有回复润色与历史上下文，不应继续说“完全没接模型或历史”。本地预览和远端版本曾不一致，实施前先核对最新实际状态。

| 内容 | 处理原则 |

| 回复润色 | 关键事实确定性展示，模型负责解释，不以关键词正则当完整事实保障 |
| 前端 | 保留可靠连接、确认和重试，重做必要的信息结构与视觉 |

目录按实际职责拆，不强制每个节点一个文件。正式实现不再长期放在拼写错误的 preparaion 下；迁移作为独立任务，修改 import、启动、测试发现和素材引用，不与新业务改动混成一个提交。

## 8. 实施顺序：每一步交付能看到的结果

不按人分工，不再为等待接口交接停止整个开发。以下是依赖顺序，不是未经验证的工期承诺。

### 阶段一：统一开发基线与规则

核对远端 main、现有 PR 与本地预览的差异，保留用户未提交文件；已有功能采用单套实现，不直接合入冲突的重复后端。更新项目执行规则中的旧分工、旧范围、单意图限制及未核实赛事措辞，使后续 AI 不再被旧文件带回原方向。Git 保持任务分支和可审查变更，不直接推 main。

产出：唯一可启动基线、当前能力清单、对应本方案的执行入口。无需为文档整理重复运行所有业务测试。

### 阶段二：先贯通一条真正的 Agent 查询链

以“最近钱花在哪 → 只看餐饮 → 超过一百的明细”为首条闭环，完成模型调用工具、读取结果、追问与自然回答，使用实际业务查询。补查询条件和对象上下文；同时解决润色不能改变业务状态的问题。

产出：真实模型使用未写死的措辞完成连续任务。避免先重构整仓数天，用户仍看不到智能变化。

### 阶段三：建立持久化银行业务底座

定义并实现客户、账户、卡和交易关系，数据库事务及重复请求结果保存；先贯通开户/演示入账 → 双边转账 → 双方查询 → 重启查询。数据库替换与业务变化分成可审查提交，保留必要回归。

产出：资金变化有双方记录，刷新重启不丢，重复请求不再扣款。

### 阶段四：补齐卡片与支付后果

申请 → 激活 → 消费 → 冻结 → 支付被拒 → 解冻 → 支付恢复 → 账单查询；加入约定消费限额。页面操作与 Agent 共用后端。

产出：卡片管理不再只改状态文字，每条状态规则有实际业务效果。

### 阶段五：完成复杂任务与恢复

加入多个操作、步骤依赖、批量一次确认、纠正、取消、新请求优先和失败后继续。用余额查询 → 选择付款账户 → 准备转账 → 确认执行 → 查看记录等实际组合验证，不创建固定“演示专用剧本”。

产出：模型能按实际结果推进，用户随时理解当前进度并接管，失败不会被说成全部成功。

### 阶段六：理财推荐闭环

建立模拟投资画像、风险评估规则及虚构产品目录，接通画像查询与补问 → 用户确认需保存的资料 → 后端筛选 → 模型解释 → 查看产品依据。推荐只提供信息，不触发购买、赎回或资金变动。

产出：完整画像可得到符合约束的候选；缺失或矛盾信息先澄清；无匹配产品时如实说明。账单行为仅作辅助，不能用账户余额代替投资预算或由模型自行生成可信风险等级。

### 阶段七：界面、结构与交付收口

界面从前述阶段逐步接入，并尽早验证桌面窗口与本地服务的一体化启动；最后完成桌面交付封装，统一视觉、交互和空态。对稳定模块做独立目录迁移和旧代码清理；检查启动与文档路径。完成全流程验收、README、架构说明、实际效果记录、PPT与备用演示视频。

若时间不足，先减少视觉装饰、登录扩展和非必要重构，保住已确认的功能目标；任何功能降级必须明确列出，不能静默称全部完成。日期及材料提交要求在交付前核对当前入口，不靠历史记录猜截止时刻。

## 9. 怎样判断已经好用

验收针对用户任务和最终数据，不以测试条数、模型能返回 JSON 或页面动画为完成证据。

| 完整任务 | 必须观察到的结果 |
|---|---|
| 桌面应用启动与重开 | 直接打开应用进入独立窗口，无需手动启动后端或浏览器；退出后重新打开，业务数据保留 |
| 开户、申请卡、激活、模拟支付 | 对象关联正确，待激活卡不能支付，成功消费进入实际账单 |
| 自然查询及连续筛选 | 同义表达可用，继承/替换条件正确，金额来自后端，可核对明细 |
| 转账补信息、改金额、确认 | 最终金额/对象正确，双方账户与关联流水同步，旧确认失效 |
| 取消或切换请求 | 未批准不扣款，能取消，不因旧任务卡死新查询 |
| 批量转账 | 一次确认展示完整列表和总额，逐笔结果真实，失败不伪造整批成功 |
| 冻结、消费被拒、解冻再支付 | 卡状态影响实际支付，不错误冻结账户的所有业务 |
| 重启与响应丢失 | 已完成记录保留，查询原结果，重复点击/重试不重复扣款 |
| 理财产品推荐 | 按预算、期限、流动性与风险评估筛选，解释有产品依据；画像不足先补问，无匹配则明确说明，不执行购买或赎回 |
| 多步骤失败 | 已完成与未执行清楚区分，可接管或停止，不假装自动撤销已完成转账 |
| 越权、注入、未知工具 | 不访问别人的业务数据、不跳过授权、不执行未开放操作 |

三层证据：业务自动化测试验证确定性规则；真实模型任务验证自然理解、工具选择和上下文；实际用户在桌面应用内用自己的说法操作验证可用性。测试替身不能替代真实模型，HTTP 测试不能冒充桌面窗口中的布局与交互测试。

建立小而覆盖关键情况的任务集：每个核心流程包括正常表达、改写、缺项、纠正、取消或失败。记录最终任务是否完成、对象/金额是否正确、不必要澄清次数、响应耗时以及有无越权或重复写入。真实测试后再给出数据，不预写成功率。

安全和账务的关键用例不应接受已知失败作为“总体通过”；开放式语言体验如不稳定，记录失败条件并修复。验收报告注明代码版本、模型配置、样例数据和测试日期，避免把历史结果套到最新代码。

VitaBench 的启发属于评估设计依据；不是要求运行原版基准才算项目通过。

## 10. 哪些内容写进最终文档，而不是全部变成代码任务

### README：给使用者

桌面应用的获取、安装（如采用安装包）、打开与退出、本地数据保存位置、模型安全配置、实际功能、演示账户、样例数据、重置方法、已知限制和复演步骤。明确真实模型/离线模式、模拟银行/真实银行的区别，不放密钥和真实个人资料。

### 架构文档：给开发者及评审

说明用户界面 → API → Agent → 业务工具 → 银行服务 → 数据库的责任关系，画一条转账和一条连续查询的时序；解释上下文、工具结果回路、确认、事务、请求重试和失败恢复。

记录为什么复用现有框架、为什么不采用多 Agent/向量库/微服务、为什么选择当前数据库，以及开源复用来源和改动。只解释真实实现，不绘制实际上不存在的生产银行架构。

项目完成后另用真实代码为用户讲解 Agent 架构：从一条输入开始，逐文件走到工具调用、确认、数据库变更和最终回复。这个教学承诺保留，不用抽象术语替代。

### 产品说明与答辩：项目现实意义

项目探索通过自然语言完成跨页面银行任务，减少用户寻找入口、记忆操作步骤和重复填写的成本。价值应由完整任务体验证明，不宣称“接个模型就解决银行数字化”。

模拟银行提供可控、可重复的验证环境，证明业务规则和助手执行效果；真实银行已有账户、卡、账务和认证系统，实际落地更可能是接入这些能力的交互与任务执行层。

更换后端适配器可以降低接入成本，但接真实银行绝不只是换 URL：还需要受授权的接口、身份与权限、字段及状态映射、认证链路、异步结果与对账、隐私和审计、运维与合规评估。未对接不声称已经具备生产可用性，也不因此取消当前模拟业务建设。

### 评估与限制说明：给复现者

介绍任务集设计、最终状态判定、自然表达改写和失败恢复测试，必要时说明借鉴 VitaBench 的交互评估思想。附实际结果和失败例子，区分已测、未测及无法验证的部分。

### 未来改进：清楚而不扩张本次承诺

第一组：已明确延后——订阅与代扣、定时转账、AA、跨期变化和异常分析。理财推荐属于本次范围；购买、赎回不在本次范围，后续是否扩展另行确认。

第二组：条件成熟再评估——正式挂失补卡、更完整的身份认证、真实银行沙箱、完整会计分录/冲正/对账、更丰富的跨场景业务、长期个性化。

第三组：非默认目标——信用卡、虚拟卡、移动端、外部账单导入、大规模分布式部署。除非后续有明确需求，不因为同行有就自动增加。
