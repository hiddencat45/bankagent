# 产品方向与优先级

> 来源：2026-10-23 的方向讨论。**结论性质，尚未开始实施。**
> 配套：[重构方案.md](重构方案.md)（文件结构，另篇）。

## 〇、你的意见（原话要点）

按提出顺序记录，保留原意：

1. **太简单** ——「所展现出来的东西是一个网页，这是第一个问题」
2. **交互不足** ——「输出太多结构化的东西」
3. **感受不到智能** ——「我们现在的大模型的确用了，但是我感受不到它的智能点在哪里」；期望像美团、高德那样「更有人味」「真的去理解用户的意图」
4. **前端要变成 APP** —— 不是网页，要「展现出来类似于点开手机银行 APP 的效果」；功能分区（转账、卡包各是一个功能），中间有 AI 入口
5. **数据要真实** —— 怀疑「转账究竟是如何完成的」，「可能仅仅只是在显示在我们页面上的两个数字」；希望转账真的改数据、查询真的读数据，「而不是一个每次都新建的字典」
6. **Agent 要能真对话** —— 「先实现真实的对话」；「跟你不符合的功能的时候他能懂意思，但是他不跟你聊」
7. **登录** —— 真实银行需要用户名 + 密码（明示**不用着急**）
8. **别过度防御性编程** —— 「别人看不到你写的那些哈希冲突或者是什么其他乱七八糟的安全代码，这只会让代码变得更加屎山」

## 一、诊断：「感受不到智能」不是模型的问题

现在的流程是**命令式**：每句话都必须落到 8 个意图之一，落不上就回：

> 请明确要办理的一项业务及相关信息。

证据在 `agent_graph.py` 的 `understand_intent`：模型返回 `scenario: null` 时直接进 `NEEDS_CLARIFICATION`，没有任何「先聊两句」的余地。

美团、高德的形态是反过来的：**聊天是默认状态，办业务是聊天里的一条分支**。理解是连续的，执行是离散的。我们把这件事做翻了——执行成了唯一出口，理解只是它的前置步骤。

所以这不是「换一个更强的模型」能解决的，是**没有给模型留出说话的位置**。

## 二、三个方向

### 2.1 前端：从网页到 APP

现状 frontend 共 1065 行（`app.mjs` 261 + `workbench.css` 526 + 其余），布局是**聊天窗口为主、卡片为辅**——这正是「像个网页」的原因。

银行 APP 的主次是反的：**功能为主**（首页 → 转账/卡包/账单）、**对话为辅**（悬浮或底部 AI 入口）。

技术上不难，难的是信息架构。**建议渐进，不推倒**：`agent-client.mjs`（SSE 对接）与卡片协议（confirm/result）是资产，继续用；只重做外壳。否则会把这几个 PR 才调通的确认卡流程再踩一遍。

### 2.2 数据：先纠正一个误解

**「只是页面上的两个数字」——不是。** `bank_backend.py` 是真实的内存后端：

- 有账户、交易流水、卡、订阅的完整结构，有归属校验
- 转账**真的**扣余额、**真的**写一条 `TRANSFER_OUT` 流水；当日累计就是从流水里算出来的（`_daily_total`）
- 有幂等键、有授权引用、有原子发布（写失败不会留下半条账）

**真正的短板只有两个**：

1. **进程内内存，重启即重置**——你说的「每次新建一个字典」说对的是这一半
2. **余额是个可变字段**（`accounts.balance_minor` 直接改），而真实银行是**双分录**：余额由流水推导，永不直接改

第 2 点比第 1 点更值钱。把双分录做对，你就能回答「为什么我们的账是对的」——这比「我们用了什么数据库」有说服力得多。

**选型建议：SQLite**，不要 PostgreSQL / MySQL / Redis。

| 方案 | 难度 | 判断 |
|---|---|---|
| **SQLite 单文件** | 中（约 2 天） | 推荐。真 SQL、真事务、零部署，能直接给评委看 schema |
| PostgreSQL / MySQL | 中高 | 要额外装服务、保演示环境，现场出问题修不动 |
| Redis / 分布式 | 高 | 不推荐，讲不清就是减分项 |

### 2.3 Agent：从命令式到对话式

**最小改造、最高收益**：加一条**对话兜底通道**。

- 识别到业务意图 → 走现有链路，一个字不改
- 识别不到 → **不再立刻拒绝**，交给模型自由回复（可以解释「我能办这几件事」、可以反问、可以接住一句闲话）
- 这条通道**没有任何执行权**，只能说话

这正好对应你说的「能懂意思，但是不跟你聊」：不匹配时它能理解你在说什么，只是礼貌地告诉你它办不了。

难度**低**（一个节点 + 一段提示词），风险也低——它碰不到钱。

## 三、跨方向的两条要求

### 3.1 登录

最简版：用户表 + 用户名/密码，`hashlib.scrypt` 一行，不做锁定、不做复杂度校验。难度低，放在最后做，但它能把「打开 APP 要先登录」这个故事讲完整。

### 3.2 代码风格：别过度防御

**同意，而且我确实写重了。** 举我自己的例子：为「后端可能返回字符串类型的余额」专门写回退分支、字段级双重类型检查、层层 `try/except`——这些情况现实中不会发生，纯属给自己加测试债。

之后的界线：

- **边界上严**（用户能触发的、会动钱的）：授权、风险分级、确认卡、拒绝原因——**保留，这些是能讲出来的卖点**
- **中间松**（不可能发生的、纯内部的）：重复校验、防御性分支——**砍掉**

一句话：**让代码为演示服务，不为假想的攻击服务。**

## 四、难度与顺序

| 优先级 | 做什么 | 难度 | 理由 |
|---|---|---|---|
| 1 | **对话兜底通道** | 低 | 直接命中「感受不到智能」，改动小、见效快 |
| 2 | **前端外壳重做** | 中偏大 | 评委第一印象，视觉冲击最大 |
| 3 | **双分录 + SQLite** | 中 | 补「账本是不是真的」这块短板 |
| 4 | 登录密码 | 低 | 收尾，让叙事完整 |
| — | 文件结构重构 | 见 [重构方案.md](重构方案.md) | 与功能并行，第一步随时可做 |

## 五、待定的三件事

1. **对话兜底的边界**：只做礼貌引导，还是允许真的闲聊几句？前者稳，后者更像美团，但要花功夫调提示词。
2. **前端**：推倒重写，还是「保留协议、只换外壳」？
3. **数据**：上 SQLite，还是保持内存但把双分录做对、并在页面上把流水摆出来给评委看？

倾向：**1 放开一点、2 渐进、3 先做双分录再决定要不要落库**——因为双分录才是「银行感」的来源，SQLite 只是把它存下来。
