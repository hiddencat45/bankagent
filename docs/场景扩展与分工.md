> **读者**：A（DSH）、B（Codex），以及双方使用的 AI 助手。
> **目的**：把「一个场景 = 一个文件」的写法和两人的领地边界固定下来，让两边能并行改代码而不冲突。
> **状态**：这是**目标规范**。第 1 节的改造尚未进行；改造完成之前，`scenarios/` 目录不存在，本文提到的路径都还不存在。

---

## 0. 一句话规则

> **新增一个业务场景 = 新建一个 `scenarios/<名字>.py`。除此之外不改任何文件。**

唯一例外：该场景需要新的后端操作时，由 **B** 在 `bank_backend.py` 里加对应函数。

如果你（AI 助手）发现为了实现一个场景，必须去改 `understand_intent`、`create_plan`、`security_policy`、`compose_response` 这些节点函数——**停下来报告**，说明规范有缺口，不要自己扩展规范。

## 2. 场景契约

一个场景模块必须定义下面 4 项（**必需**），可选定义另外 4 项。

### 2.1 必需项

```python
SCENARIO: str
# 场景唯一标识，小写英文，与文件名一致。例："bills"

INTENTS: dict[str, dict]
# 意图声明表，见 2.3

def execute(operation: str, params: dict, state: dict) -> dict:
    """执行该场景的操作，返回结构化 result。
    只读操作直接返回数据；写操作必须调用 bank_backend 里对应的函数，
    不得在这里直接修改任何状态。"""

def render(result: dict, state: dict) -> str:
    """把结构化 result 翻译成给用户看的自然语言。
    不得改写 status，不得在 result 里没有成功事实时宣称成功。"""
```

### 2.2 可选项

```python
CLARIFY_LABELS: dict[str, str] = {}
# 槽位名 → 中文名，用于生成澄清提示。例：{"period": "时间范围"}
# 未定义的槽位直接用槽位名本身。

def resolve(state: dict) -> dict:
    """把用户说的实体解析成服务端 ID，返回要合并进 State 的字段。
    例：把"尾号1234的卡"解析成 card_id。
    模型永远不能自己构造 ID，必须由这里查询服务端。"""

def validate(plan_entry: dict) -> bool:
    """校验该操作独有的参数规则。默认只检查 operation 在白名单内。
    例：金额必须为正、时间范围必须合法。"""

def risk(state: dict) -> str:
    """返回 "GREEN" / "YELLOW" / "RED" / "DENY"。
    定义了本函数时，以它为准，忽略 INTENTS 表里的 risk 字段。"""
```

### 2.3 `INTENTS` 表的字段

```python
INTENTS = {
    "<INTENT_NAME>": {          # 大写英文，例："BILLS_ANALYSIS"
        "keywords": [...],      # 必需。用于匹配用户 message 的关键词
        "slots": {...},         # 可选。槽位名 → 提取用正则
        "required": [...],      # 可选。这些槽位缺失时进入澄清
        "operation": "...",     # 必需。操作名，会汇总进 ALLOWED_OPERATIONS
        "risk": "GREEN",        # 必需。GREEN / YELLOW / RED / DENY
    },
}
```

### 2.4 匹配优先级

调度器按 `scenarios/__init__.py` 的发现顺序（模块名排序）依次询问每个场景。

- **关键词不得重复**：`tests/test_contracts.py` 会断言任意两个场景的关键词集合不相交。
- 同一场景内多个意图命中时，**`keywords` 更长的意图优先**。

## 3. 完整示例：账单分析

`scenarios/bills.py` 的全部内容：

```python
"""账单分析场景：查消费明细、按类别汇总、发现异常。

纯查询，不碰资金，因此是 GREEN。三个操作全部只读。
"""

SCENARIO = "bills"

INTENTS = {
    "BILLS_QUERY": {
        "keywords": ["账单", "消费明细", "花了多少", "支出"],
        "slots": {
            "period": r"(本月|上月|近\d+天|近\d+个月)",
            "group_by": r"(按类别|按商户|按时间)",
        },
        "required": [],                      # period 缺省就是本月，不强制澄清
        "operation": "QUERY_BILLS",
        "risk": "GREEN",
    },
    "BILLS_ANOMALY": {
        "keywords": ["异常消费", "可疑交易", "有没有问题"],
        "slots": {"period": r"(本月|上月|近\d+天)"},
        "required": ["period"],
        "operation": "DETECT_ANOMALY",
        "risk": "GREEN",
    },
}

CLARIFY_LABELS = {"period": "时间范围", "group_by": "统计维度"}


def execute(operation, params, state):
    from bank_backend import query_bills, detect_anomalies

    if operation == "QUERY_BILLS":
        return query_bills(
            state["account_id"],
            params.get("period", "本月"),
            params.get("group_by"),
        )
    if operation == "DETECT_ANOMALY":
        return detect_anomalies(state["account_id"], params["period"])
    raise ValueError(f"bills 场景不支持操作 {operation!r}")


def render(result, state):
    if result.get("operation") == "QUERY_BILLS":
        return (
            f"{result['period']}共支出 {result['total']:.2f} 元，"
            f"最大一类是{result['top_category']}。"
        )
    if result.get("operation") == "DETECT_ANOMALY":
        n = len(result["anomalies"])
        if n == 0:
            return f"{result['period']}没有发现异常消费。"
        return f"{result['period']}发现 {n} 笔异常消费，可查看明细。"
    return "操作未完成。"
```

对比：改造前加这个场景要改 12 处；改造后只新建这 1 个文件。

### 4.2 解耦的关键：先冻结后端函数签名

A 写 `card.py` 时需要 `bank_backend.freeze_card` 等函数存在，而这些函数归 B 实现。为避免互相等待：

> **改造阶段，A 把 6 个场景需要的后端函数签名一次性写进 `bank_backend.py`，函数体统一 `raise NotImplementedError`，并写清 docstring（参数、返回结构、风险提示）。这份签名就是两人之间的契约。**

签名冻结后：

- A 可以先写 `card.py`，用 `try/except NotImplementedError` 或测试 stub 先把图跑通
- B 按签名逐个实现，实现一个就把对应的 `NotImplementedError` 换掉
- 两边都不需要等对方

## 5. 硬规则（AI 助手必须遵守）

### 5.1 不许做的事

1. **不许为了实现场景去改第 2 节之外的节点函数。** 需要新钩子时停下来报告。
2. **不许把有资金影响或不可逆的操作标成 `GREEN`。** 冻结卡片、挂失、下单、取消代扣至少是 `YELLOW`；挂失不可逆，应为 `RED`。
3. **不许让模型写这些字段**：`user_id`、`account_id`、`contact_id`、`card_id`、`product_code`、`risk_level`、`operation_hash`、`challenge_id`、`authorized`、`balance`、`result`。它们只能由服务端或调度器写入。
4. **不许新增第三方依赖。**
5. **不许修改或放宽已有测试的断言。**
6. **不许把密钥、口令、OTP、真实卡号、身份证号、手机号写进代码、测试、样例数据或日志。**
7. **不许在 `interrupt()` 之前制造不可重复的副作用**（发短信、扣款、生成流水号）。
8. **不许用 `float` 做资金运算**，用 `Decimal` 或整数分。
9. **不许在 `render()` 里宣称 result 中不存在的成功事实。**
10. **不许声称实现了本文档没有的能力。**

### 5.2 关键词冲突

两个场景不能争抢同一个关键词。这会导致用户的话被路由到错误场景，而且是**静默错误**。

`tests/test_contracts.py` 必须包含这条断言：

```python
def test_keywords_are_disjoint():
    seen = {}
    for sc in all_scenarios():
        for intent, spec in sc.INTENTS.items():
            for kw in spec["keywords"]:
                assert kw not in seen, f"关键词 {kw!r} 被 {seen[kw]} 和 {sc.SCENARIO} 同时占用"
                seen[kw] = f"{sc.SCENARIO}.{intent}"
```

### 5.3 每个场景必须有的测试

- 意图识别：这条话能路由到本场景
- 槽位缺失：缺必需槽位时进入澄清，且提示文案包含中文槽位名
- 风险等级：声明的等级与实际 `security_policy` 输出一致
- 执行：`execute()` 对每个 `operation` 都能返回预期的 result 结构
- 回复：`render()` 不编造事实

## 6. 特殊情况：「跨场景联动」

**它不是一个普通场景，不要照第 2 节的契约实现。**

其他 5 个场景都是**单个业务操作**；跨场景联动是**把多个操作编排成有依赖的长任务**，需要：任务表、幂等键、重试上限与退避、补偿流程、人工接管入口。

处理方式，二选一：

- **A**（完整版）：单独作为第三块，由 A 主写、B 辅助，D4 一起做。它需要 `agent_task` 表和一组编排原语，不放进 `scenarios/`。
- **B**（答辩够用版，推荐）：降级成"演示两个场景串起来"，例如「账单发现异常订阅 → 直接发起取消」，写成 `scenarios/cross.py` 但只做**固定编排**，不实现任务表。

选 B 时，在 `scenarios/cross.py` 顶部写明这是演示级实现，并列出完整版还缺什么。**不要把它说成已经实现了通用编排能力。**

## 7. 验收标准

一个场景算完成，需要同时满足：

1. `.\scripts\check.ps1` 全绿
2. 第 5.3 节的五类测试齐全，且测试**真的会失败**（改坏代码能测出来）
3. 关键词不与其他场景冲突
4. 没有改动第 4.1 节之外的文件
5. 没有违背第 5.1 节的任何一条
6. `render()` 的输出与实际 result 结构一致

**AI 助手自己的判断不算完成依据。**
