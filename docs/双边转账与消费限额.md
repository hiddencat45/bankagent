# 双边转账与消费限额

## 转账的实际记账

演示联系人张伟绑定 account-002，李娜绑定新增的零余额 account-003。联系人映射是服务端固定演示配置，当前没有编辑入口；未知或未绑定的收款账户拒绝执行。原公开转账签名和授权参数仍为 contact_id、amount_minor、currency。

成功转账在同一 SQLite 事务中完成付款方扣款、收款方入账、两笔关联流水和成功回执。流水分别为 TRANSFER_OUT / TRANSFER_IN，拥有同一个 transfer_id，互相记录 related_transaction_id，并保存对手账户和交易后余额。对外账单仍只投影当前账户的交易事实，不暴露其他账户余额。转入与转出都不算消费。

自己的其他账户按名称在服务端查找，生成 `own:<账户引用>` 作为受控收款引用，执行时再次核对本人归属；当前付款账户不能作为目标。同名账户或与联系人重名时不任选一条。自己账户与联系人转账共用执行函数、限额、授权、原子事务和幂等逻辑。

示例：先开户「储蓄账户」，保持默认付款账户，发送“给储蓄账户转50元”，确认后两个账户余额分别减少和增加50元。新账户原有的1,000元是单独记录的演示入账，与转账无关。切换到储蓄账户后可查询到账余额；也可向“默认演示账户”转回。

成功回执新增 transfer_id、incoming_transaction_id，原 transaction_id 仍指付款流水。同请求重试返回原回执，不再次写入任何一方。数据库写入失败时双方变化及回执一起回滚。

账单查询现在也返回已有的 transfer_id、related_transaction_id，桌面账单明细展示转账编号及双方流水编号，便于关联核对。仅增加可选字段，原字段不变；不返回对手账户标识或余额，不扩大查询归属。旧单边流水没有关联字段，保持原样。调用方为账单场景、HTTP/SSE 结果、桌面 QueryClient 和开发工作台；旧调用方可忽略新增字段，数据库版本不变。

## 消费控制

每张卡默认单笔上限5,000元、当日累计上限10,000元。用户可通过“查询限额”“设置限额”按钮或对话操作；设置需要确认，查询无需确认。支持0至1,000,000元，单笔不得高于每日，使用整数分。零限额会拒绝新的卡支付。

- `query_card_limits(context, card_id)` 返回 display_name、currency、single_limit_minor、daily_limit_minor、used_today_minor、business_date。
- `set_card_limits(context, card_id, single_limit_minor, daily_limit_minor)` 对应 SET_CARD_LIMITS，WRITE/YELLOW。授权绑定全部参数；成功回执返回卡名、币种与两项限额。
- `pay_by_card` 在同一数据库事务中重新检查卡状态、余额、单笔和当日累计限额。超限返回 CARD_SINGLE_LIMIT_EXCEEDED / CARD_DAILY_LIMIT_EXCEEDED，无扣款和成功流水。

每日范围按后端业务日期（+08:00）计算，仅累计当天明确关联该卡 card_id 的 EXPENSE。默认历史样例没有卡片关联，不能猜测归到某张卡；转账、其他卡支付和演示入账不占该卡额度。调低到已用额度以下不会撤销历史消费，但后续支付被拒。冻结或解冻不清零累计消费，修改限额不改变卡状态。

离线表达：`查询限额「日常消费卡」`、`设置限额「日常消费卡」单笔100元，每日200元`。真实模型可理解改写，确认卡须核对卡名与两项金额。每次付款仍单独确认；消费限额不是授权，也不是信用额度。

## 存储升级与历史边界

SQLite 快照格式升级到版本2，新数据库直接创建版本2。版本1在事务中自动迁移，只为身份和名称匹配的两个固定演示联系人补目标引用，必要时增加李娜的零余额账户。自定义联系人不猜测收款方，目标冲突时保持未绑定并拒绝新转账。旧程序只认版本1，会拒绝打开新账本，避免跨版本继续写入。

已有余额、流水、建库时间和幂等回执保留。**旧版已执行的单边转账不自动补收款入账**：缺少原始可信收款绑定，不能在升级时制造历史到账。旧请求重放仍返回历史回执，不补扣款或补入账。只有升级后的新转账才保证双方记录完整。

限额在卡记录上保存；未设置的卡使用上述默认值。无重置账本、重新导入种子或删除用户数据的步骤。#56 原版本没有普通界面的演示客户切换入口；后续任务分支已补固定名单入口，见 [受控切换与入账](桌面应用.md#受控切换演示客户与查看入账)。本人多账户可在桌面直接切换验证。

## 整批转账（2026-10-27，待审）

产品决定：用户明确选择“整批全有或全无”，取代旧方案里仅作为建议的逐笔独立提交。先解析完整列表、展示每位收款人、金额、总额与原子语义，一次确认绑定有序列表。任一项修改均使旧确认失效。实现限制为每批2至10项，继续沿用单笔金额限制；合计与当日累计决定认证等级，批量不会降级认证。原生桌面的 RED 操作仍须独立认证，目前只开放取消，未伪造生产认证入口。

复用路径：单笔与批量共享 `_transfer_authorization`、`_check_transfer`、`_post_transfer`。批量在既有 `_transaction` 内加载账本，逐项校验/暂存于同一私有副本，全部成功才一次发布余额、双边流水和回执。没有第二个资金后端、新表或反向转账补偿。任一项业务拒绝时丢弃全部暂存资金变化，保存拒绝回执；数据库提交失败则账本与回执一起回滚。暂存过的步骤不是成功交易，失败批次只显示失败项和未执行项。

结果与恢复：
- 成功：全部项为成功，每项附流水和转账编号，共用 batch_id。
- 业务失败：整批 committed=false；触发失败的项为失败，其他项为未执行，无成功项、无新增资金流水。回执同时展示整批合计与办理前余额。
- 取消：全部未执行，不扣款。取消确认未执行资金服务，因此不新增持久化业务回执。
- 执行异常或响应丢失：不宣称已成功或全部失败；重试原确认，以原幂等键查询/执行同一整批。已提交时重放原回执；尚未提交时仍必须通过原授权和资金校验。业务拒绝回执也幂等，不能因后来余额变化就自动变为成功付款。
- 重启后：旧会话/确认不自动恢复，新会话可用桌面“批量回执”核对成功或业务拒绝的批次，也可从本月流水核对 batch_id 与 transfer_id。不能因为没看到聊天回复就重新发起相同付款。

契约与调用方：新增注册操作 BATCH_TRANSFER / QUERY_TRANSFER_BATCHES，沿用现有 BackendResult 和六类 SSE 事件；没有新增写 HTTP 端点。模型 prepare_batch_transfer 只接受 items[{recipient_name, amount}]，服务端转换为受控 contact_id、整数分和币种。声明模块提供列表候选 schema、校验及逐项缺项说明，现有普通表单及字符串候选不变。对只缺第二项收款人的请求，只追问第二项并保留第一项。

新增只读 `GET /bank/transfer-batches`，身份取当前服务端会话，不接受 user_id/account_id；只返回当前账户的整批回执（包括失败），不泄露幂等键或授权记录。桌面按钮和 Agent 查询共用 query_transfer_batches。确认卡新增 items、total_minor、currency、atomic=true；桌面核对列表合计和风险绑定，逐项展示，未知/不一致卡片不能批准。账单流水新增可选 batch_id。SQLite版本仍为2，沿用快照及回执格式，不重置旧余额或补历史款项。
