## 1. 公共状态（A 起草）

### 1.1 字段分组

按 `场景扩展与分工.md` §3.1 的四组划分。这四组是**通用承载字段**，新增场景只在 `candidate_params` / `params` 里加键，不新增顶层 State 字段。

| 组 | 字段 | 写入方 |
|---|---|---|
| 可信上下文 | `user_id`、`account_id`、`request_id` | 只由服务端注入。公开请求不得提供 |
| 用户输入 | `message` | API 层 |
| 候选理解 | `scenario`、`intent`、`candidate_params`、`missing_fields` | 规则或模型。**未受信任** |
| 已校验操作 | `operation`、`params` | Python 校验并解析实体后生成 |
| 安全与结果 | `risk_level`、`operation_hash`、`challenge_id`、`authorized`、`result`、`status` | 公共安全层与后端 |
| 输出 | `response` | 回复节点 |

### 1.2 类型声明

```python
from typing import Any, Literal, TypedDict

TopLevelStatus = Literal[
    "PROCESSING", "NEEDS_CLARIFICATION", "AWAITING_CONFIRMATION",
    "AWAITING_AUTHENTICATION", "COMPLETED", "REJECTED", "FAILED", "PENDING",
]

class BankAgentState(TypedDict, total=False):
    # ── 可信上下文：服务端注入，模型与前端一律不可写 ──
    user_id: str
    account_id: str
    request_id: str

    # ── 用户输入 ──
    message: str

    # ── 候选理解：未受信任，不得直接成为执行参数 ──
    scenario: str                      # 场景标识，如 "bills"
    intent: str                        # 意图名，如 "BILLS_QUERY"
    candidate_params: dict[str, Any]   # 槽位名 → 候选值；键由场景的 slots 声明
    missing_fields: list[str]          # 缺失槽位名，非空则走澄清

    # ── 已校验操作：实体已解析，参数已规范化 ──
    operation: str                     # 如 "TRANSFER"，由 Python 映射生成
    params: dict[str, Any]             # 规范化后的参数；目标 ID 来自受控后端查询

    # ── 安全与结果：只由公共安全层与后端生成 ──
    risk_level: Literal["GREEN", "YELLOW", "RED", "DENY"]
    operation_hash: str
    challenge_id: str
    authorized: bool
    result: dict[str, Any]
    status: "TopLevelStatus"

    # ── 输出 ──
    response: str
```

**说明：单操作而非计划列表。** 阶段 2 的余额查询、转账、账单查询都是单操作，所以用 `operation` + `params`（与 `场景扩展与分工.md` §3.1 一致）。跨场景联动需要的是**固定编排**（同文件 §7），不是通用计划列表，到时由 A 增加编排入口，**不要现在预埋 `plan: list`**。

### 1.3 谁不能写什么

`AGENTS.md` §四已经列了不可写字段。落到本接口，**以下字段在任何场景、任何节点里都不接受来自模型或 API 请求的值**：

```
user_id  account_id  request_id  contact_id  card_id  product_code
risk_level  operation_hash  challenge_id  authorized  balance  result
idempotency_key  authorization_ref  daily_transfer_total_minor
```

`params` 里的目标 ID 必须由 `resolve()` 查受控后端得到，**不能来自 `candidate_params`**。

### 1.4 状态取值

**两个 status 要分开**，别混用：

**后端结果状态**（`result["status"]`，B 的后端返回）：

```
COMPLETED | REJECTED | FAILED | PENDING
```

**图顶层状态**（`state["status"]`，公共调度器设置）：

```
PROCESSING              新请求已开始，尚未产出结果
NEEDS_CLARIFICATION     信息不足，等用户补充，本轮结束
AWAITING_CONFIRMATION   已 interrupt，等用户确认
AWAITING_AUTHENTICATION 已 interrupt，等强认证
COMPLETED               操作成功完成
REJECTED                业务拒绝：越权、余额不足、策略 DENY、用户取消
FAILED                  意外失败
PENDING                 已提交未完成（异步，本阶段不实现，仅保留取值）
```

**映射规则**（`场景扩展与分工.md` §3.3 要求，必须实现且测试）：

| 后端 `result.status` | 图顶层 `status` |
|---|---|
| `COMPLETED` | `COMPLETED` |
| `REJECTED` | `REJECTED` |
| `FAILED` | `FAILED` |
| `PENDING` | `PENDING` |
| 后端抛异常 | `FAILED`（由公共边界捕获，转脱敏诊断） |

**不得因为后端函数正常返回就一律标 `COMPLETED`。**

### 1.5 清空与恢复语义

轮次分类由 A 的公共层处理，不交给 B 的业务后端。每次先校验会话归属和互斥，再按以下三种情况处理：

| 类型 | 服务端判定依据 | 保留与清理 |
|---|---|---|
| 恢复中断 | resume 合法、同一用户/thread/challenge，且服务端挑战属于该待恢复请求 | 沿用原 request_id 和已绑定参数，不清空；非法恢复直接拒绝，不降级成普通新请求 |
| 澄清续轮 | 普通 message；最近 checkpoint 为 NEEDS_CLARIFICATION；属于同一用户；服务端记录的澄清期限未到（30 分钟）；满足下述续轮条件 | 仅保留待澄清任务的候选槽位并合并本轮明确提供的候选，重新解析/校验；生成新 request_id，清空旧执行结果、安全决策及授权，状态设 PROCESSING |
| 新请求 | 既非合法恢复，也不满足澄清续轮条件，例如没有待补任务、已超时或明确换话题 | 生成新 request_id，清空旧候选及全部操作、安全和结果字段，状态设 PROCESSING |

续轮条件：本轮明确识别到的 `(scenario, intent)` 与待补任务相同；**或本轮没有独立业务意图，但能唯一对应上一轮正在询问的槽位**。后者保证“给张伟转钱”后只回复“300 元”仍能补全。不能因为缺少新意图就强制用户重述。无法区分补槽与新话题时先澄清，不猜测；明确换话题按新请求。改收款人也是候选更新，必须重新 resolve，不能复用旧 contact_id。

清空字段为 scenario、intent、candidate_params、missing_fields、operation、params、risk_level、operation_hash、challenge_id、authorized、result、response；澄清续轮仅例外保留候选意图与槽位，不保留旧 params 或授权。澄清期限保存在服务端待补任务元数据中，用注入时钟判定，不能由前端/model 设置，也不需要为此新增公共顶层 State 字段。

同一 thread 同时只允许一个运行；等待确认期间拒绝普通新消息（409 RUN_BUSY），先取消当前挑战才能重新办理。换用户访问旧 thread 一律拒绝；新用户只能创建自己的会话，不能“按新请求”读取他人的旧槽位。

## 2. 场景模块契约（A 起草）

### 2.1 必需项

```python
SCENARIO: str
INTENTS: dict[str, IntentSpec]

def execute(operation: str, params: dict[str, Any], context: "TrustedContext") -> dict[str, Any]: ...
def render(result: dict[str, Any]) -> str: ...
```

```python
class IntentSpec(TypedDict):
    keywords: list[str]                 # 离线规则模式的匹配词
    slots: dict[str, str]               # 槽位名 → 提取用正则
    required: list[str]                 # 缺失则澄清
    operation: str                      # 会汇总进 ALLOWED_OPERATIONS
    effect: Literal["READ", "WRITE"]
    risk: Literal["GREEN", "YELLOW", "RED", "DENY"]   # 静态最低风险
```

### 2.2 可选项

```python
CLARIFY_LABELS: dict[str, str] = {}                            # 槽位名 → 中文名
def resolve(candidate_params: dict, context: "TrustedContext") -> dict: ...
def validate(operation: str, params: dict) -> bool: ...
def risk(operation: str, params: dict, context: "TrustedContext") -> str: ...
```

规则（均来自 `场景扩展与分工.md` §3.2、§5）：

- `execute` **只分发到后端并返回统一结果**，不在场景里修改账户、卡片或协议状态。
- `render` 只读结果，不调用工具、不改状态，**失败或处理中不得显示成功**。
- `resolve` 遇到未知或歧义实体必须进入澄清，**不能任选一条**；访问范围限当前用户。
- `validate` 是附加校验；**省略钩子不等于跳过校验**，公共层始终检查必填项、类型和操作归属。
- `risk` **只能升高**，不得低于声明的 `risk`；返回非法或缺失值属于配置错误，必须阻止执行。

### 2.3 context 类型

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class TrustedContext:
    user_id: str
    account_id: str
    request_id: str

@dataclass(frozen=True)
class WriteContext(TrustedContext):
    authorization_ref: str    # 服务端授权记录的引用，不含凭证
    idempotency_key: str
```

本次 B 建议确认以上 `WriteContext`。服务端构造它，模型/前端不得提供；授权引用本身不证明已授权，后端必须按 §3.4 重查记录。恢复后的执行节点按可信 request_id 取得该引用，不从客户端 resume 读取。凭证本身不得进入 context。

### 2.4 冻结范围内的示例：账单查询

```python
SCENARIO = "bills"

INTENTS = {
    "BILLS_QUERY": {
        "keywords": ["账单", "消费明细", "花了多少", "支出"],
        "slots": {"period": r"(本月|上月|近\d+天)"},
        "required": [],
        "operation": "QUERY_BILLS",
        "effect": "READ",
        "risk": "GREEN",
    },
}

CLARIFY_LABELS = {"period": "时间范围"}


def execute(operation, params, context):
    from bank_backend import query_bills
    return query_bills(
        context=context,
        start=params["start"],  # datetime.date，解析后统一生成
        end=params["end"],
    )


def render(result):
    if result["status"] != "COMPLETED":
        return "账单查询未完成。"
    data = result["data"]
    label = f"{data['start']} 至 {data['end']}（结束日不含）"
    if data["top_category"] is None:
        return f"{label}没有消费支出记录。"
    amount = data["total_minor"]
    money = f"{amount // 100}.{amount % 100:02d}"  # 展示也不经过 float
    return f"{label}共消费 {money} 元，最大一类是{data['top_category']}。"
```

## 3. 后端契约（B 补充，待 A 确认）

### 3.1 统一结果

```python
class BackendResult(TypedDict):
    operation: str
    status: Literal["COMPLETED", "REJECTED", "FAILED", "PENDING"]
    data: dict[str, Any] | None
    error_code: str | None      # 成功时为 None
```

B 同意四字段结构。COMPLETED 时 data 必须是该操作成功结构，error_code 为 None；REJECTED/FAILED 时 data 为 None，error_code 必填。PENDING 留作后续，本阶段三个操作不返回它。返回值必须可 JSON 序列化；日期在返回中使用 ISO 字符串，金额为整数分。

### 3.2 三个业务操作与辅助查询（实现均归 B）

| 操作 | 效果 | 函数 | 归属 |
|---|---|---|---|
| `GET_BALANCE` | READ / GREEN | `get_balance` | B |
| `TRANSFER` | WRITE / 最低 YELLOW | `execute_transfer`，仅授权后调用 | B |
| `QUERY_BILLS` | READ / GREEN | `query_bills` | B |

**命名提案**：新契约把原草案的 `PREPARE_TRANSFER` 改为 `TRANSFER`，表示贯穿准备、确认、执行的业务操作。准备阶段只生成 params、风险和挑战，不扣款；`execute_transfer` 是服务端私有执行函数，不暴露为模型工具。旧教学文件暂不改，阶段 1 单独做兼容迁移与授权/整数分改造，不能把旧测试放宽来掩盖差异。

```python
from datetime import date

def get_balance(*, context: TrustedContext) -> BackendResult: ...
def execute_transfer(*, context: WriteContext, contact_id: str,
                     amount_minor: int, currency: str = "CNY") -> BackendResult: ...
def query_bills(*, context: TrustedContext, start: date, end: date) -> BackendResult: ...

def find_contacts(*, context: TrustedContext, name: str) -> list[dict[str, str]]: ...
```

- context.user_id/account_id 来自会话，所有查询与写入校验归属。未知账户和跨用户账户统一拒绝，不泄露存在性。
- contact_id 来自 `find_contacts`，返回只含当前用户的 `{contact_id, display_name}`，无匹配为空列表，多个匹配走澄清。初版精确姓名匹配；不支持别名时明确说明。
- 转账规范化 params 恰为 `{contact_id, amount_minor, currency}`。金额为严格正整数（bool 也拒绝），不接收 float；用户金额字符串用 Decimal 转换，超过两位小数拒绝，不暗自四舍五入。只支持 CNY。
- 账单候选 period 在 resolve 阶段变成 date 型的 start/end；缺省本月。以演示参考日为准，本月为当月 1 日至下月 1 日，上月同理；近 N 天含参考日，结束为参考日次日，开始为结束日减 N 天；N 为 1–366。显式范围必须 start < end 且不超过 366 天，不生成未来交易。
- `find_contacts` 是受控辅助查询，不作为新的模型意图或业务 operation 注册。归属失败抛受控拒绝，由公共边界转成当前业务操作的 REJECTED；不能把后端失败伪装成“无联系人”。

成功 data 的字段与口径：

| 操作 | data（字段均必需） |
|---|---|
| GET_BALANCE | `balance_minor: int`、`currency: "CNY"`、`daily_transfer_total_minor: int`（参考日已成功转出的合计，供服务端风控） |
| TRANSFER | `transaction_id: str`、`recipient: str`、`amount_minor: int`、`currency: "CNY"`、`remaining_balance_minor: int` |
| QUERY_BILLS | `start/end: str`、`currency: "CNY"`、`total_minor: int`、`by_category: dict[str,int]`、`top_category: str或None`、`transactions: list`、`anomalies: list` |

transactions 每项为 `{transaction_id, occurred_at, kind, amount_minor, category, merchant}`。occurred_at 为带 +08:00 的 ISO 时间；kind 为 INCOME / EXPENSE / TRANSFER_OUT，amount_minor 为非负金额，kind 决定账本方向；merchant 可为 None。列表按发生时间、交易 ID 升序。

GET_BALANCE 的 daily_transfer_total_minor 只供可信风控节点使用，不进入 Prompt、SSE、render 或页面；对外结果投影仅含 balance_minor/currency。内部原始结果不能直接交给通用消息/卡片序列化器。

账单范围匹配记录上限为 MAX_BILL_TRANSACTIONS=100，先由后端计数，超限返回 REJECTED/TOO_MANY_TRANSACTIONS，提示缩短日期范围，不静默截断明细、统计或异常证据。未超限才生成并返回完整结果；模型和页面最多收到这 100 条，不把超限全年记录塞进上下文。本阶段不做分页。

total_minor 是 EXPENSE 的合计，收入与转账不计入“消费”；by_category 的合计必须等于 total_minor。top_category 按金额降序取第一，金额相同时按类别名排序。空消费时 top_category=None、by_category={}，不凭空返回最大类别。

anomalies 每项为 `{type: "POSSIBLE_DUPLICATE", evidence: list[str]}`。初版仅检测同账户、同非空商户、同金额、60 秒内的不同消费交易，按商户/金额分组、时间升序，以组内最早一笔为窗口起点生成至少两笔的证据组；每笔最多进入一组，超过窗口则开启下一组。证据必须在本次返回的 transactions 中；表述为“疑似”，不声称已认定欺诈。测试真值标签不参与检测，也不返回给模型。

业务错误返回 REJECTED，error_code 取以下值：

| error_code | 条件 |
|---|---|
| ACCOUNT_NOT_ACCESSIBLE | 未知账户或非当前用户账户，读写均适用 |
| CONTACT_NOT_ACCESSIBLE | 未知或不属于当前用户的联系人 |
| INVALID_AMOUNT / UNSUPPORTED_CURRENCY / INVALID_DATE_RANGE | 金额、币种、日期校验失败 |
| TOO_MANY_TRANSACTIONS | 账单范围匹配记录超过上限，需缩短范围 |
| USER_CANCELLED | 用户拒绝当前挑战，由公共层生成 REJECTED 结果；不是新的顶层 status，也不调用扣款后端 |
| AUTHORIZATION_REQUIRED / AUTHORIZATION_INVALID | 缺授权引用 / 授权不存在、过期、拒绝、绑定不符或强度不足 |
| IDEMPOTENCY_CONFLICT | 同一用户账户下同键不同操作或参数 |
| INSUFFICIENT_BALANCE / TRANSFER_LIMIT_EXCEEDED | 余额不足 / 单笔超过 1000000 分 |
| REAUTHORIZATION_REQUIRED | 并发转账导致累计风险升高，现有授权强度不够，需重新生成挑战 |

未预期异常由公共边界转 FAILED/INTERNAL，不暴露堆栈。余额查询失败不可返回零余额；账单服务失败不可返回空账单。

### 3.4 授权、风险与幂等交接

A 实现服务端挑战/授权表和只读授权查询；B 的后端依赖注入该查询函数，测试注入可信替身。避免后端 import 图模块形成循环，也不让 execute_transfer 接受客户端传入的 authorized。

```python
def lookup_authorization(authorization_ref: str) -> dict | None: ...  # A 实现
```

记录字段：user_id、account_id、request_id、operation（TRANSFER）、params（规范化三字段）、operation_hash、challenge_id、risk_level（YELLOW/RED）、decision（APPROVED/REJECTED）、expires_at（带时区 datetime）、idempotency_key。均为服务端事实，不含 OTP；返回快照而非可修改的存储对象。哈希由 A 的同一个纯函数计算，B 注入使用；绑定可信用户/账户/request_id、operation 和全部规范化 params，按稳定 JSON 规则处理，不能另造一套算法。

- A 准备阶段调用 get_balance 取得服务端累计量；累计加本笔 <=100000 分为 YELLOW，否则 RED，单笔 >1000000 分 DENY。B 扣款前在锁内复查同一规则；授权等级不足拒绝并要求重新确认/认证，不靠客户端提供累计值。
- 由 A 在 bank_types.py 定义 YELLOW_DAILY_LIMIT_MINOR=100000、TRANSFER_SINGLE_LIMIT_MINOR=1000000 和 MAX_BILL_TRANSACTIONS=100，A/B 引用同一处常量，不能各写一份阈值。操作哈希纯函数由 A 提供并注入后端，不放进仅含声明的 bank_types.py；实际实现位置在落地 PR 说明。
- B 校验 context 与授权记录中的用户、账户、请求、幂等键一致，decision=APPROVED、未过期、params/hash 匹配且认证强度足够。A 对授权记录的终态修改与 B 写入需采用同一进程内互斥机制，避免撤销/重置与扣款竞态；具体锁注入方式在实现 PR 说明，不改上述语义。
- 幂等键由服务端按本次逻辑写操作生成，首次执行和 HTTP 重试都复用；不能每次恢复随机生成。同一键的指纹包含 request_id、operation、params。
- 锁内先检查可信 context 和键的归属：已成功同键同指纹返回存储结果，即使授权随后过期也不重新扣款；同键不同指纹拒绝。首次执行才复查有效授权和余额，随后原子保存扣款、流水、累计和成功结果。
- 拒绝不占用成功幂等结果。同键同指纹重放返回已存结果；同键异指纹拒绝，旧成功键不得用于新操作。参数变化必须使用新请求、新挑战和新幂等键。重放结果是“当时剩余余额”，页面要显示当前余额时重新查询。
- 内存 Demo 不接真实收款银行，只记录当前用户的转出账本；不虚构外部到账。进程重启丢失业务变更、授权及幂等记录，此限制必须在 README 展示。

### 3.5 重置及会话边界

B 提供 `reset_demo_data() -> None`，仅由受控 Demo API 调用，不注册为模型工具。它在与写入相同的锁内恢复整个固定数据集；A 同时使旧会话、图 Checkpoint、挑战和授权失效，重置与运行互斥，重置后页面重新取得演示会话，不能让旧确认卡继续扣款。

A 负责 API 路由、登录/模拟会话与权限检查，B 负责数据重置及页面按钮。`POST /demo/reset` 仅显式 Demo 模式开放，要求已验证的演示会话，仅本地部署；非 Demo 模式返回 404。它不清理文件或真实银行数据，也不接收 user_id/account_id。

## 4. API 契约（A 起草）

### 4.1 请求

```
POST /agent/chat
Authorization: Bearer <session>      # 服务端据此解析 user_id / account_id
Content-Type: application/json
```

```jsonc
{
  "thread_id": "conv-0001",          // 会话标识；首次可省略，由服务端生成并返回
  "message": "给张伟转 500 元",       // 用户输入；恢复中断时为 null
  "resume": null                     // 恢复时见 4.3
}
```

**公开请求不得包含** `user_id`、`account_id`、`balance`、`risk_level`、`authorized` 等任何可信字段。收到即拒绝（`400 UNTRUSTED_FIELD`），**不做"忽略后继续"**——静默忽略会掩盖前端 bug。

响应为 `text/event-stream`（SSE）。

请求只能是“非空 message + resume=null”或“message=null + resume 对象”，禁止同时提供两者。已有 thread_id/challenge_id 只是客户端回传的服务端引用，必须重查归属，不算允许前端创建可信 ID。禁止字段检查同时覆盖嵌套 resume，额外的 params/operation/authorized 均拒绝。新建会话由服务端选择已登录用户的当前账户。

页面用 fetch 读取 POST 的 SSE，不使用只能 GET 的原生 EventSource。服务端在流开始前完成身份、会话、请求结构校验；不合法时返回 HTTP JSON `{code, message}`，其中未登录为 401、参数结构为 400、会话不可访问为 404、RUN_BUSY 为 409；其余参数错误用 INVALID_REQUEST。流开始后的错误通过 error 事件发送，随后 done，不把堆栈返回前端。

### 4.2 SSE 事件

事件类型冻结为下面 6 个。**页面显示的一切必须来自这里，不得用定时器伪造进度。**

```
event: status
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "step": "started", "status": "PROCESSING"}

event: message
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "text": "本月共支出 1234.00 元，最大一类是餐饮。"}

event: card
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "type": "result", "payload": {"operation": "GET_BALANCE", "status": "COMPLETED", "data": {"balance_minor": 500000, "currency": "CNY"}, "error_code": null}}

event: interrupt
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "kind": "CONFIRMATION", "challenge_id": "ch-0001",
       "operation_hash": "ab12…", "prompt": "确认向张伟转账 500.00 元？"}

event: error
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "code": "BACKEND_UNAVAILABLE", "message": "账单服务暂时不可用。"}

event: done
data: {"thread_id": "conv-0001", "request_id": "req-0001", "mode": "offline", "status": "COMPLETED"}
```

卡片的 `type` 冻结三个：`confirm`（确认卡）、`evidence`（证据卡）、`result`（结果卡）。`payload` 的业务字段由场景声明，阶段 2 只需要账单证据卡与转账确认卡两种。

上面是六种独立事件的完整信封示例，不是一条业务流；**每条事件的 data 都包含同一 thread_id/request_id/mode**，mode 为 offline / model，由服务端配置决定。本轮首次 status 必须在业务事件之前发出，页面从它保存新建会话 ID。恢复沿用原 request_id；普通新请求或澄清续轮生成新 ID。status 的 step 可为 started / understood / validated / awaiting_confirmation / awaiting_authentication / executing / finished，必须在对应步骤实际发生后发出，不保证每次都有所有步骤。

阶段 2 卡片 payload 最小字段如下，B 按此渲染，A 从后端事实或待确认操作构造：

| type | payload |
|---|---|
| confirm | `operation: "TRANSFER"`、`recipient: str`、`amount_minor: int`、`currency: "CNY"`、`risk_level: "YELLOW"或"RED"`、`challenge_id: str`、`operation_hash: str`、`expires_at: ISO时间` |
| evidence | `operation: "QUERY_BILLS"`、`data: §3.2 的账单成功 data` |
| result | 对外安全投影的 BackendResult：GET_BALANCE 的 data 只含 balance_minor/currency，转账与失败结构沿用 §3.2；不能包含内部风控字段 |

确认卡不应在缺少 interrupt 事件时启用按钮。interrupt 与 confirm 的挑战必须一致；同一 request/challenge 的重发卡片更新原卡，不新增一次扣款入口。返回的内部业务 ID 不等于凭证；页面不得擅自把它们作为新的执行参数提交。

每轮顺序：首次 status → 实际进度/消息/卡片 → 最终 done。暂停时先发 confirm 卡片和 interrupt，再发 done（status 为 AWAITING_CONFIRMATION/AWAITING_AUTHENTICATION）；澄清时 message 后 done（NEEDS_CLARIFICATION）。done 仅表示本次 HTTP 流结束，不表示业务成功。完成后 done.status 与 result.status 一致；业务拒绝发 result 卡片和 REJECTED 的 done，服务/模型故障发 error 后 FAILED 的 done。页面保留等待卡直至批准、拒绝或失效；不把 PROCESSING 或断流当成功，也不自动重放 POST 造成新操作。

模型超时如需切到 offline，用户应明确选择后发起新请求，服务端不得在原请求中静默换模式；模式切换端点本次不冻结。

**轨迹只显示业务步骤、风险摘要和证据，不展示模型内部思维或敏感信息。**

### 4.3 中断与恢复

关键约束来自 `AGENTS.md` §四 与 `场景扩展与分工.md` §5：**授权/认证结果必须来自服务端查询，不得从 resume 载荷读取。**

流程：

1. 图确认/认证节点调用 `interrupt()` 暂停。API 取得暂停结果后，由 A 的服务端以 `(user_id, request_id, operation_hash)` 幂等登记待处理 challenge（含归属、规范化参数、风险、过期时间和幂等键），再发出卡片与 interrupt 事件。challenge ID 在准备阶段生成并保持稳定；含 interrupt 的节点在中断前不得随机分配 ID、写不可重复记录或发送认证消息。
2. 客户端让用户操作，然后把结果提交回来：

```jsonc
{
  "thread_id": "conv-0001",
  "message": null,
  "resume": {
    "challenge_id": "ch-0001",
    "decision": "approve",     // "approve" | "reject"；拒绝适用于两类挑战
    "otp": null                // 普通确认不提供；强认证值只在 API 内短暂消费，示例不包含凭证
  }
}
```

3. **服务端**校验 challenge 归属当前用户与请求、未过期、`operation_hash` 与当前参数一致；认证类则校验 OTP。通过后**把授权结果写进服务端记录**。
4. 服务端用 `Command(resume=...)` 恢复图。**恢复后的节点只读服务端记录**，不读 `decision`、不读 `otp`。
5. `otp` 与任何凭证**在 API 层消费完毕即丢弃**：不进 State、不进 Checkpoint、不进普通日志。

challenge 默认 5 分钟有效，expires_at 由服务端时钟生成。RED 的 approve 必须通过独立服务端认证校验；初版可注入模拟认证服务，在界面明确标注“模拟认证”，不得以客户端一个布尔值或固定口令作为认证结果。decision=reject 只记录拒绝并恢复图，顶层 status=REJECTED，结构化 result 为 operation=TRANSFER、status=REJECTED、data=None、error_code=USER_CANCELLED；不新增顶层状态、不写批准授权、不调用扣款后端。API 与后端均不记录凭证。

同一挑战重复提交相同终态返回已保存状态；批准后再拒绝或拒绝后再批准均为 409 CHALLENGE_INVALID，不改变已完成业务。图恢复失败时服务端保留授权和同一个幂等键供安全重试；不能重新生成一份操作。过期或参数不符时拒绝，不恢复扣款。

**要点**：`resume` 载荷是"给服务端验证的输入"，不是"授权凭证"。这一条是现有教学代码（`auth_token == "demo-otp-ok"`）必须改掉的地方。

### 4.4 其它端点

```
GET  /health            实际检查各依赖状态，页面据此显示，不写死"正常"
POST /demo/reset        路由与鉴权 A 实现；数据重置 B 实现，边界见 3.5
```

`GET /health` 返回 `{status: "ok"或"degraded", mode: "offline"或"model", backend: "ok"或"unavailable", model: "ok"或"unavailable"或"not_configured"}`；offline 下未配置模型不影响核心服务。reset 成功返回 `{status: "COMPLETED"}`，页面清空旧会话与卡片。演示会话的发放方式由 A 在首个 API PR 中提供受控入口与启动说明，不能让页面硬编码用户或访问令牌；本草案不虚构已存在的登录实现。

### 4.5 错误码

```
UNTRUSTED_FIELD         请求含可信字段
INVALID_REQUEST         message/resume 组合、字段类型或额外字段不符合契约
RUN_BUSY                同一会话运行中或尚有未处理挑战
CONVERSATION_NOT_FOUND  thread_id 不存在或不属于当前用户
CHALLENGE_INVALID       challenge 不存在、过期、不属当前用户或与参数不匹配
CHALLENGE_STATE_MISMATCH  operation_hash 与当前参数不一致（参数被改过，须重新确认）
MODEL_UNAVAILABLE       真实模型超时或不可用 → 明确提示，可切离线模式
MODEL_OUTPUT_INVALID    模型输出非法结构或含可信字段 → 拒绝或澄清
BACKEND_UNAVAILABLE     后端依赖不可用
INTERNAL                未预期错误，记录脱敏诊断
```

**任何情况下都不得**：静默把模型失败当成成功、把 `NotImplementedError` 转成成功、在缺少有效授权时执行写操作。
